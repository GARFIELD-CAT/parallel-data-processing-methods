# MPI-подобная библиотека обмена сообщениями

Учебная реализация механизма обмена сообщениями между узлами распределённой
системы в стиле **MPI (Message Passing Interface)**. Узлы общаются по реальным
**TCP-сокетам**, реализованы операции «точка-точка» и коллективные операции
(Broadcast, Gather, Scatter, AllGather, Reduce, AllReduce, Barrier). Готовые
библиотеки MPI и фреймворки распределённых вычислений не использовались — всё
написано вручную поверх `System.Net.Sockets`.

---

## 1. Как запустить

Требуется **.NET SDK 10.0**. Из папки с `HW_11.csproj`:

```bash
dotnet run
```

Программа поднимает кластер из 4 узлов на `127.0.0.1` (порты 9000–9003),
демонстрирует все операции, затем выключает лог и прогоняет бенчмарки, после чего
тестирует масштабируемость на 2/4/8 узлах и печатает итоговую сводку.

---

## 2. Главная идея (модель выполнения)

Все узлы живут **в одном процессе**, но каждый узел — это самостоятельный объект
со своим TCP-портом, и общаются они через **настоящие сокеты** на `127.0.0.1`.
Узел с рангом `r` слушает порт `9000 + r`.

Используется модель **SPMD** (Single Program, Multiple Data): один и тот же код
исполняется всеми узлами одновременно. В демонстрации и бенчмарках это сделано
через запуск задачи на каждый узел и `Task.WhenAll`. То есть когда вызывается,
например, `Broadcast`, его одновременно вызывают все узлы — кто-то в роли корня,
кто-то в роли получателя; они согласованно обмениваются сообщениями и сходятся к
общему результату.

Топология сети — **полная сетка**: каждый узел при старте подключается ко всем
остальным. Поэтому любая пара узлов может обмениваться напрямую, а коллективы
строятся уже поверх этого как логические алгоритмы (дерево, кольцо).

---

## 3. Архитектура: слои и кто за что отвечает

```
Program.cs                — сценарий: поднять кластер, демо, бенчмарки, сводка
   |  создаёт N штук
   v
MpiCommunicator           — публичное лицо MPI: Send/Receive/Broadcast/Reduce/...
   |  владеет                       |  делегирует коллективы
   v                                v
MpiNode                   CollectiveOperations  — алгоритмы дерева/кольца/барьера
   |  использует
   v
TcpClientWrapper, Mailbox — сокет с кадрированием; потокобезопасная очередь писем

MessageTypes              — общий «язык»: формат MpiMessage + сериализация (JSON)
MpiBenchmark              — замеры времени/объёма/числа сообщений (Stopwatch)
```

Принцип — **разделение ответственности**: каждый слой не знает лишнего о
соседях. `CollectiveOperations` не работает с сокетами напрямую — он вызывает
`SendRaw`/`ReceiveRaw` у коммуникатора. `MpiCommunicator` не разбирает байты — это
делает `MpiNode`. `MpiNode` не знает, что такое «Broadcast» — он просто доставляет
сообщения по рангу и тегу.

## 4. Разбор по классам

### MessageTypes.cs — формат сообщения и сериализация

**`MpiMessage`** — единица обмена. Поля строго по ТЗ: `MessageId` (Guid),
`MessageType` (строка: `"SEND"`, `"BROADCAST"`, ...), `SourceRank`,
`DestinationRank`, `Tag`, `Payload` (`byte[]`), `Timestamp`. Добавлено служебное
поле `PayloadType` — имя .NET-типа полезных данных, чтобы на приёме знать, во что
их распаковывать.

**`MessageTypeNames`** и **`MessageTags`** — наборы констант для типов и тегов.
Тег — это метка, по которой получатель отличает сообщения разных операций
(например, у Broadcast тег 100, у Gather — 200, у барьера — отдельные 500/501).

**`PointToPointMessage` / `CollectiveMessage` / `BarrierMessage`** — подклассы
`MpiMessage`, требуемые заданием. По сети всё ездит как базовый `MpiMessage`.

**Сериализация в два уровня** — это важный для защиты момент:

1. `PayloadCodec` превращает **полезные данные** (число, строку, массив) в
   JSON-байты и запоминает имя их типа (`AssemblyQualifiedName`). На приёме по
   имени типа находит `Type` и десериализует обратно.
2. `MessageCodec` превращает **всё сообщение целиком** в JSON-байты, которые уже
   уходят в сокет.

**`GatherAccumulator`** — «контейнер», который путешествует по кольцу в операции
Gather. Хранит ранги и значения узлов в виде простых списков (`List<int>`,
`List<string>`), поэтому надёжно сериализуется. На корне метод `ToOrderedArray`
восстанавливает массив значений, упорядоченный по рангам.

### MpiNode.cs — сетевой слой одного узла

**`TcpClientWrapper`** — обёртка над `TcpClient`. Главное здесь — **кадрирование**:
TCP передаёт поток байт без границ, поэтому перед каждым сообщением пишется его
длина: `[4 байта длины N][N байт тела]`. На приёме сначала читаем 4 байта длины,
затем ровно N байт (`ReadExactly` дочитывает, пока не наберёт нужное число байт).
Запись защищена `SemaphoreSlim`, чтобы два потока не перемешали свои кадры.

**`Mailbox`** — потокобезопасная очередь входящих сообщений. Метод `Receive`
ждёт сообщение, подходящее под фильтр (источник + тип + тег), и либо возвращает
его, либо по истечении таймаута бросает `TimeoutException`. Реализован на
`SemaphoreSlim`: при добавлении письма вызывается `Release` (сигнал «появилось
письмо»), ожидающий просыпается через `WaitAsync` и заново проверяет очередь.

**`MpiNode`** — собственно узел:

- `Start()` — поднимает `TcpListener` на своём порту и запускает фоновый цикл
  приёма подключений `AcceptLoop`. Перед стартом ставит `SO_REUSEADDR`, чтобы порт
  можно было переиспользовать в тестах масштабируемости.
- `ConnectToNode(...)` — подключается к соседу (с таймаутом и повторными
  попытками), сразу шлёт приветствие `HELLO`. Если за все попытки подключиться не
  удалось — **бросает исключение** (ошибки подключения не игнорируются).
- `AcceptLoop` / `ReaderLoop` — принимают входящие соединения и читают из них
  кадры; каждое сообщение разбирается и отдаётся в `ProcessMessage`.
- `ProcessMessage` — если сообщение адресовано этому узлу, кладёт его в `Mailbox`
  и поднимает событие `MessageReceived`; иначе пытается маршрутизировать дальше.
- `RouteMessage` — находит соединение к получателю и отправляет байты; если
  соединения нет — бросает исключение.
- `SendObject` / `ReceiveObject` — «высокоуровневые» отправка и приём: упаковать
  объект → отправить; дождаться по фильтру → распаковать.

### MpiCommunicator.cs — публичный MPI-интерфейс

Это то, с чем работает прикладной код. Внутри владеет одним `MpiNode` (сеть) и
одним `CollectiveOperations` (алгоритмы) и «склеивает» их.

- Точка-точка: `Send`, `Receive`, `SendReceive`.
- Внутренние `SendRaw`/`ReceiveRaw` — то, чем пользуются коллективы.
- Коллективы `Broadcast`, `Gather`, `Scatter`, `AllGather`, `Reduce`,
  `AllReduce`, `Barrier` делегируются в `CollectiveOperations`.
- `AllGather` = Gather к корню 0, корень упаковывает всё в `GatherAccumulator`,
  затем Broadcast этого пакета всем; каждый распаковывает в массив.
- `AllReduce` = Reduce к корню 0, затем Broadcast результата всем.
- Порт узла = `BasePort (9000) + nodeId`; таймаут операций по умолчанию 15 с.

### CollectiveOperations.cs — алгоритмы коллективов

Подробно разобраны в разделе 6. Здесь только перечень: `ImplementBroadcast`
(дерево), `ImplementGather` (кольцо), `ImplementScatter`, `ImplementReduce`
(дерево), `ImplementBarrier`.

### MpiBenchmark.cs — замеры

- `BenchmarkPointToPoint` — ping-pong между узлами 0 и 1, возвращает среднее,
  минимальное и максимальное время.
- `BenchmarkBroadcast` — время рассылки и число отправленных сообщений за
  операцию.
- `BenchmarkGather` — время сбора и объём данных.
- `BenchmarkReduce` — время редукции и результат (сумма рангов).

Время измеряется `Stopwatch`; перед бенчмарками логирование выключается, чтобы
вывод в консоль не искажал замеры.

### Program.cs — сценарий

Класс `Cluster` создаёт N коммуникаторов, запускает их, соединяет в полную сетку.
`Main` прогоняет демонстрацию корректности всех операций, затем бенчмарки, затем
тест масштабируемости (2/4/8 узлов) и печатает сводку в формате из задания.

## 5. Как сообщение проходит весь путь (на примере `Send`)

Полезно уметь рассказать «жизнь одного сообщения» от и до:

1. `comm.Send(1, "привет")` → `SendRaw` → `node.SendObject(...)`.
2. `PayloadCodec.Encode("привет")` → JSON-байты + имя типа `System.String`.
3. Собирается `MpiMessage` (тип `SEND`, тег `Default`, `SourceRank`,
   `DestinationRank=1`, `Payload`, `PayloadType`).
4. `RouteMessage` находит соединение к узлу 1 и через `MessageCodec.Serialize`
   превращает сообщение в байты, добавляет 4-байтовый префикс длины и пишет в сокет.
5. На узле 1 `ReaderLoop` читает кадр, `MessageCodec.Deserialize` восстанавливает
   `MpiMessage`, `ProcessMessage` видит `DestinationRank == 1` и кладёт письмо в
   `Mailbox`.
6. Узел 1 в это время ждёт в `comm.Receive(0)` → `ReceiveObject` → `Mailbox.Receive`
   с фильтром «source=0, type=SEND, tag=Default». Письмо подходит — возвращается.
7. `PayloadCodec.Decode` по имени типа распаковывает байты обратно в строку.

## 6. Алгоритмы коллективных операций (ключевая часть защиты)

### Broadcast — рассылка по двоичному дереву

Чтобы не слать N-1 сообщений последовательно (медленно), узлы выстраиваются в
двоичное дерево. Вводится **виртуальный ранг** `v = (me - root + n) mod n` — сдвиг
нумерации так, чтобы корень стал нулём; тогда у узла `v` дети всегда `2v+1` и
`2v+2`, а родитель — `(v-1)/2`. Каждый узел получает данные **один раз** от
родителя и пересылает максимум двум детям. Глубина дерева ~ log2(N), поэтому
рассылка идёт «волной» за ~log2(N) шагов, а не за N.

Трассировка для n=4, root=0 (виртуальные ранги совпадают с реальными):

- узел 0 (корень) отправляет детям 1 и 2;
- узел 1 получил → отправляет своему ребёнку 3;
- узлы 2 и 3 — листья, только получают.

### Gather — сбор по кольцу

Данные собираются, проходя по цепочке узлов и накапливаясь в одном «контейнере»
(`GatherAccumulator`). Стартовый узел `(root+1) mod n` создаёт контейнер, кладёт
своё значение и передаёт следующему по кольцу. Каждый промежуточный узел получает
контейнер, добавляет себя и отдаёт дальше. Корень получает контейнер последним,
добавляет своё значение и восстанавливает массив, упорядоченный по рангам.

Трассировка для n=4, root=0: стартует узел 1, кольцо 1 → 2 → 3 → 0. Контейнер
собирает значения узлов 1, 2, 3, 0; на корне `ToOrderedArray` раскладывает их по
позициям 0..3. Преимущество кольца — корень не «захлёбывается» от одновременных
сообщений всех узлов: нагрузка размазана по цепочке.

### Scatter — раздача кусков

Корень отправляет узлу `i` его кусок `data[i]`, свой кусок `data[root]` оставляет
себе. Остальные узлы просто принимают свой кусок от корня.

### Reduce — свёртка по дереву снизу вверх

Дерево то же, что в Broadcast, но данные текут в обратную сторону. Лист отправляет
своё значение родителю; родитель получает значения от детей, применяет к ним
функцию `op` (например, сумму), сворачивает со своим значением и передаёт выше.
Корень получает итог.

Трассировка для n=4, root=0, op = сумма, значение = ранг:

- лист 3 шлёт 3 родителю 1; узел 1 считает 1+3=4 и шлёт корню;
- лист 2 шлёт 2 корню;
- корень 0: 0 + 4 (от узла 1) + 2 (от узла 2) = **6** — что и есть 0+1+2+3.

### Barrier — барьерная синхронизация

Схема «сбор + разрешение». Координатор (узел 0) дожидается сообщения «я дошёл» от
всех остальных (тег `BarrierArrive`), после чего рассылает всем «можно идти
дальше» (тег `BarrierRelease`). Остальные узлы шлют «я дошёл» и ждут разрешения.
Так ни один узел не проходит барьер, пока до него не дошли все.

## 7. Таймауты и обработка ошибок

- **Приём** (`Mailbox.Receive`) ограничен по времени через
  `CancellationTokenSource(timeout)`. По истечении времени бросается
  `TimeoutException` — операция не висит вечно. При этом внешняя отмена и
  собственный таймаут различаются: для отмены бросается `OperationCanceledException`
  с понятным текстом, для таймаута — `TimeoutException`.
- **Подключение** (`ConnectToNode`) — с таймаутом 2 с на попытку и повторами; при
  полном провале бросается исключение (ошибки подключения не замалчиваются).
- **Маршрутизация** (`RouteMessage`) — если соединения к получателю нет, бросается
  исключение, а не тихое игнорирование.

Почему таймаут именно с исключением: в распределённой системе нельзя отличить
«сообщение задерживается» от «не придёт никогда». Таймаут превращает потенциальный
вечный висяк в видимую, диагностируемую ошибку, которую вызывающий код может
поймать и обработать (повтор, лог, корректное завершение).

## 9. Обоснование проектных решений (что отвечать на «почему так?»)

**Почему JSON, а не `BinaryFormatter`?** ТЗ рекомендует на выбор `BinaryFormatter`
**или** `JsonSerializer`. `BinaryFormatter` удалён из среды выполнения .NET 9/10 и
при использовании бросает исключение, поэтому выбран `System.Text.Json`: он
безопасен, читается глазами при отладке и полностью покрывает учебные сценарии.

**Почему `SemaphoreSlim`, а не `ManualResetEvent`/`TaskCompletionSource`?** ТЗ
называет их как рекомендацию, но не обязательность. `SemaphoreSlim` удобно работает
в `async`-коде (`WaitAsync` не блокирует поток) и естественно играет роль сигнала
«в ящике появилось письмо».

**Почему полная сетка, а не маршрутизация?** Полная сетка проще и надёжнее для
учебного масштаба (единицы–десятки узлов): любая пара общается напрямую, не нужно
вычислять маршруты. Метод `RouteMessage` оставлен как точка расширения.

**Почему два уровня сериализации?** Полезные данные могут быть любого типа, и нам
нужно знать, во что их распаковывать, — отсюда хранение имени типа рядом с байтами.
Само сообщение — отдельная сущность с метаданными (ранги, тег), поэтому оно
сериализуется вторым уровнем.

**Где здесь асинхронность?** Приём подключений и чтение из каждого соединения
крутятся в фоновых задачах; отправка/приём — `async`; узлы в демо и бенчмарках
работают одновременно через `Task.WhenAll`.

## 10. Вероятные вопросы преподавателя и ответы

**«Что будет, если узел не ответит?»** Сработает таймаут в `Mailbox.Receive` и
вылетит `TimeoutException`; вызывающий код может его поймать. Без таймаута система
зависла бы навсегда — поэтому он обязателен.

**«Зачем 4 байта длины перед сообщением?»** TCP — это поток байт без границ
сообщений. Префикс длины позволяет на приёме понять, сколько байт составляют одно
сообщение, и не «склеить» два сообщения и не разорвать одно.

**«Чем тег отличается от типа сообщения?»** Тип говорит, что это за операция
(`BROADCAST`, `GATHER`), а тег — числовая метка для фильтрации на приёме, чтобы
не перепутать, например, фазу «прибытия» и «разрешения» в барьере. Приём всегда
фильтрует по совокупности источник+тип+тег.

**«Почему Broadcast по дереву быстрее последовательной рассылки?»**
Последовательно корень шлёт N-1 сообщений по очереди — это N-1 шагов. В дереве
каждый узел шлёт максимум двум детям, и рассылка идёт параллельными «волнами» за
~log2(N) шагов.

**«Почему Gather по кольцу, а не все шлют корню сразу?»** Если все N-1 узлов шлют
корню одновременно, корень становится узким местом. В кольце нагрузка
распределена: каждый узел получает один контейнер и отправляет один.

**«Где гарантия, что Reduce посчитает правильно при любом дереве?»** Свёртка идёт
строго снизу вверх: каждый узел сначала собирает значения всех своих детей, потом
отправляет результат родителю. Корень получает значение только после того, как
поддеревья полностью свёрнуты.

**«Используете ли глобальные переменные для координации?»** Нет. Всё состояние
(соединения, почтовый ящик, счётчики) хранится внутри объектов узла и
коммуникатора; узлы договариваются исключительно сообщениями. Глобальный
`Logger.Enabled` — это только переключатель вывода, он не участвует в координации.

## 11. Известные ограничения

- **Фильтр приёма** учитывает источник, тип и тег, но не порядковый номер
  операции. Это работает, потому что коллективы в тестах не накладываются по
  времени (каждый дожидается завершения через `Task.WhenAll`). В более общем случае
  стоило бы добавить идентификатор операции, как делают коммуникаторы в настоящем MPI.
- **Почтовый ящик на семафоре** рассчитан на то, что на одном узле в каждый момент
  не больше одного ожидающего приёма. В текущем коде это так (все операции на узле
  последовательны), но при двух одновременных приёмах на одном ящике потребовалась
  бы более аккуратная синхронизация.
- **Масштаб.** Полная сетка хороша для единиц–десятков узлов; для сотен узлов число
  соединений (N в квадрате) стало бы проблемой, и понадобилась бы маршрутизация.

Эти ограничения осознанные и не мешают учебным сценариям 2/4/8 узлов.
