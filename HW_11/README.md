# MpiDemo — простая MPI-подобная библиотека обмена сообщениями

Учебный проект распределённых вычислений. Реализованы базовые примитивы обмена
сообщениями в стиле MPI поверх TCP-сокетов с **полностью асинхронным
неблокирующим вводом-выводом** (используются `async/await`, `Task`).

Учебная реализация механизма обмена сообщениями между узлами распределённой
системы в стиле **MPI (Message Passing Interface)**. Узлы общаются по реальным
**TCP-сокетам**, поддерживаются операции **точка-точка** (Send / Receive /
SendReceive) и **коллективные** операции (Broadcast, Gather, Scatter, AllGather,
Reduce, AllReduce, Barrier). Готовые библиотеки MPI (MS-MPI, OpenMPI) и
фреймворки распределённых вычислений (Akka.NET, Orleans) **не использовались** —
всё написано вручную поверх `System.Net.Sockets`.

Проект сделан как учебный пример

---

## Требования

- **.NET SDK 10.0** (проект проверялся под 10.0.201).
- Операционная система — любая (Windows / Linux / macOS): используется только
  стандартная библиотека .NET.
- Свободные TCP-порты `9000…9000 + (число узлов − 1)` на `127.0.0.1`.

## Как собрать и запустить

Из корневой директории проекта (там, где лежит `MpiDemo.csproj`):

```bash
dotnet run
```

или раздельно:

```bash
dotnet build      # компиляция
dotnet run        # запуск демонстрации + бенчмарков
```

Программа сама поднимает кластер из 4 узлов на одной машине, прогоняет все
операции для проверки корректности, затем запускает замеры производительности и
печатает сводную статистику.

### Как файлы связаны между собой

```
Program.cs
   │ создаёт N штук
   ▼
MpiCommunicator  ──владеет──►  MpiNode  ──использует──►  TcpClientWrapper, Mailbox

```

## Ключевые идеи реализации

### 1. Модель «один процесс — много узлов» (SPMD)

Все узлы кластера живут в одном процессе, но **каждый узел — это отдельный объект
со своим TCP-портом**, и общаются они через настоящие сокеты на `127.0.0.1`. Узел
с рангом `r` слушает порт `9000 + r`. Это удобно для учёбы: запустили одну
программу — получили целый «кластер».

Каждый узел выполняет одну и ту же программу одновременно (модель SPMD,
Single Program Multiple Data). В демонстрации это сделано через `Task.Run` для
каждого узла и `Task.WaitAll`.

### 2. Как устроено сообщение

Каждое сообщение — это объект `MpiMessage` со служебными полями: уникальный
`MessageId`, тип (`"SEND"`, `"BROADCAST"`, …), ранги отправителя и получателя,
**тег** (для фильтрации, обязательное требование), полезная нагрузка `Payload`
(байты) и временная метка.

Перед отправкой сообщение превращается в байты в два шага:

1. **Полезные данные** (число, строка, массив) → JSON-байты. Рядом сохраняется
   имя .NET-типа, чтобы на приёмной стороне понять, как их восстановить.
2. **Всё сообщение** целиком → JSON-байты, которые и уходят в сокет.

### 3. Кадрирование: «сколько байт читать»

TCP — это поток байт без границ. Чтобы понять, где заканчивается одно сообщение и
начинается следующее, перед каждым сообщением пишется его длина:

```
[ 4 байта длины N ][ N байт самого сообщения ]
```

Приёмник сначала читает 4 байта длины, затем ровно `N` байт тела. Этим занимается
`TcpClientWrapper` (метод `ReadFrame`).

### 4. Почтовый ящик (Mailbox) и приём по фильтру

Входящие сообщения складываются в `Mailbox`. Когда программа вызывает
`Receive`, она просит ящик выдать сообщение, подходящее под фильтр
(нужный отправитель + тип + тег). Если такого пока нет — поток **ждёт**
(`Monitor.Wait`), пока сетевой поток не положит новое сообщение и не разбудит
ожидающих (`Monitor.PulseAll`).

### 5. Тайм-ауты (обязательное требование)

Ожидание в `Mailbox.Receive` **ограничено по времени**. Если за отведённый срок
(по умолчанию 15 секунд) нужное сообщение не пришло — выбрасывается
`TimeoutException`. Так операции не «зависают» навсегда. Тайм-аут также стоит на
этапе подключения: `ConnectToNode` делает несколько попыток с тайм-аутом и, если
сосед недоступен, **бросает исключение, а не молча игнорирует** ошибку (тоже
требование задания).

### 6. Теги сообщений

У каждого типа операции свой набор тегов (`MessageTags`): обычная отправка —
`Default`, Broadcast — `Broadcast`, барьер — отдельные теги «прибыл» и
«разрешаю идти дальше». Приём всегда фильтрует сообщения по тегу, поэтому,
например, ответ барьера не перепутается с обычным сообщением.

### 7. Оптимизация коллективов (за баллы)

- **Broadcast и Reduce — по дереву.** Узлы выстраиваются в двоичное дерево
  относительно корня. Каждый узел получает данные один раз и пересылает максимум
  двум детям. Число «шагов» — примерно `log₂(N)` вместо `N` при наивной
  последовательной рассылке.
- **Gather — по кольцу.** Данные собираются, проходя по цепочке узлов
  `0 → 1 → 2 → … → root`, накапливаясь в одном пакете. Это снижает нагрузку на
  корневой узел по сравнению со схемой «все шлют корню одновременно».

### 8. Никаких глобальных переменных для координации

Состояние (соединения, почтовый ящик, счётчики) хранится **внутри объектов**
узла и коммуникатора. Узлы договариваются только через сообщения. Это прямо
соответствует запрету задания на глобальные переменные для координации.

## Пример использования

Минимальный сценарий «отправил-принял» между двумя узлами (псевдо-набросок в
стиле того, что делает `Program.cs`):

```csharp
// создаём два коммуникатора: ранги 0 и 1, всего узлов 2
var comm0 = new MpiCommunicator(0, 2);
var comm1 = new MpiCommunicator(1, 2);

comm0.Start();
comm1.Start();          // оба слушают свои порты (9000 и 9001)

comm0.ConnectToPeers(); // соединяемся друг с другом
comm1.ConnectToPeers();

// узел 0 шлёт строку узлу 1, узел 1 её принимает
// (в реальной программе эти две строки выполняются в разных Task одновременно)
comm0.Send(destination: 1, message: "Привет, узел 1!");
object received = comm1.Receive(source: 0);   // -> "Привет, узел 1!"

comm0.Stop();
comm1.Stop();
```

Коллективные операции вызываются так же просто, каждым узлом одновременно:

```csharp
// рассылка от корня 0 всем узлам
object value = comm.Broadcast(message: 42, root: 0);

// редукция: сумма локальных значений всех узлов, результат у корня 0
object sum = comm.Reduce(localValue: comm.Rank,
                         operation: (a, b) => (int)a + (int)b,
                         root: 0);

// барьер: все узлы дожидаются друг друга в этой точке
comm.Barrier();
```

После запуска `dotnet run` программа печатает:

1. Лог демонстрации каждой операции (точка-точка, Broadcast, Scatter, Gather,
   Reduce, AllReduce, AllGather, Barrier) — чтобы видеть, что результаты верные.
2. Сводку в формате из задания:

```

  ...

Коллективные операции:
```

Конкретные числа зависят от вашей машины — впишите их в отчёт после запуска.

| Требование / запрет                       | Где выполнено                                                      |

| Замер времени `Stopwatch`                 | `MpiBenchmark.cs`                                                  |
